# Writing and publishing a blog post

Everything you need to publish on `/blog`. The short version: **drop an `.mdx` file into
`content/blog/` and push.** The filename is the URL slug.

---

## 1. Create the file

```text
content/blog/my-post-title.mdx   →   https://mfalme.runs-on.dev/blog/my-post-title
```

Use lowercase words separated by hyphens. No `.mdx` extension in the slug, no date prefix,
no numbering. The slug is permanent once published — changing it later requires a redirect
(see §7).

A complete, copyable template is checked in at
[`content/blog/how-to-write-a-post.mdx`](./how-to-write-a-post.mdx). It ships as a draft, so
it is not published and is safe to copy, edit, or delete.

---

## 2. Frontmatter

YAML between two `---` lines at the top of the file.

| Field | Required | Notes |
| --- | --- | --- |
| `title` | yes | Post headline, rendered as the `<h1>`. Also the `<title>` and OG title. |
| `description` | yes | One or two sentences. Used for the card, the meta description, the RSS item and the OG description. |
| `datePublished` | yes | `YYYY-MM-DD`. Drives sort order. |
| `dateModified` | no | `YYYY-MM-DD`. Renders an "Updated" line when it differs from published. |
| `publishOn` | no | `YYYY-MM-DD`. Withhold the post until this date. See [SCHEDULING.md](../SCHEDULING.md). |
| `tags` | no | YAML list of strings. Powers the filter pills and related-post matching. |
| `cover` | no | Absolute path to an image under `public/`. Omit for a generated placeholder. |
| `draft` | no | `true` hides the post from the site entirely. |

**Malformed frontmatter fails the build** rather than rendering a broken page. That is
deliberate — you find out at deploy time, not from a reader.

```mdx
---
title: "I Built Atlas, Then Started Breaking It on Purpose"
description: "What a distributed systems lab taught me about Raft and network partitions."
datePublished: "2026-10-06"
tags: ["Distributed Systems", "Raft", "Go", "Failure Injection"]
---
```

## 3. Writing the body

**Start at `##`.** The `<h1>` is rendered from the `title` field, so a leading `#` would
produce two headings.

`##` and `###` headings automatically populate the "On this page" table of contents. Their
anchor ids are generated by the `rehype-slug` plugin, and `lib/blog.ts` reproduces the same
slug algorithm to build the TOC links — keep headings punctuation-light and the two stay in
step.

### What the renderer supports

Styling comes from [`mdx-components.tsx`](../../mdx-components.tsx) at the repo root, which
maps every element onto the Bauhaus design tokens so posts match the guides. It supports:

- **Headings** `##` `###` `####`, with automatic anchor ids
- **Paragraphs, bold, italic, inline `code`**
- **Lists** — unordered (`-`) and ordered (`1.`), with red markers
- **Tables** — GFM syntax, styled like the comparison tables in the guides
- **Fenced code blocks** — rendered on the ink background in Spline Sans Mono
- **Blockquotes** — rendered as the callout treatment the guides use
- **Images** — `![alt](/images/blog/photo.jpg)`, routed through `next/image`
- **Rules** — `---` between sections

To restyle every post at once, edit `mdx-components.tsx`. Do not add per-post CSS.

### ASCII diagrams work

Box-drawing characters render correctly inside a fenced `text` block, so architecture
diagrams are fine:

````mdx
```text
  Client
    │
    ▼
   API ──► Queue ──► Worker
```
````

## 4. Cover images

Optional. Put files in `public/images/blog/`, then:

```mdx
cover: "/images/blog/photo.jpg"
```

A post **without** a cover renders a generated Bauhaus composition instead, seeded from the
slug. The seed makes it deterministic — the same post always draws the same shapes, on
every build and every device — so the index grid stays visually even whether or not every
post has an image.

A cover, when present, is also used as the post's `og:image`, so the link preview in Slack,
WhatsApp and iMessage shows the photo rather than the generated card.

Keep covers roughly 16:9. Portrait images are cropped hard by the card's fixed aspect ratio.

---

## 5. Drafts

Set `draft: true`. A draft is invisible: not in the index, not in the tag pills, not in the
feed, not in the sitemap, and its URL returns 404.

> **Do not leave `content/blog/` completely empty.** `app/(site)/blog/[slug]/page.tsx` imports
> MDX through a template-literal specifier that Turbopack resolves against a glob of the
> directory. With zero files there is nothing to resolve and **the build fails** with
> `Module not found: Can't resolve '@/content/blog/'`. Keeping one draft or post in the
> directory avoids this.

## 6. Publishing

```bash
npm run build   # must pass
git add content/blog/my-post-title.mdx
git commit -m "blog: add my post title"
git push
```

Vercel deploys on push to `master`. That is the whole workflow — no CMS, no database, no
admin panel, no service to pay for.

> **If your post has a future `publishOn` date, it will not appear on its own.** A static site
> has no clock — the post goes live on the next deploy after the date. See
> [SCHEDULING.md](../../SCHEDULING.md) and [PUBLISH-REMINDER.md](../../PUBLISH-REMINDER.md)
> for the push command.

### Definition of done

```bash
npx tsc --noEmit   # 0 errors
npm run lint       # 0 errors (3 pre-existing warnings are tolerated)
npm run build      # must succeed
```

There is no test suite. These three are the gates.

## 7. Changing a slug after publishing

Renaming the file changes the URL. Because published slugs get indexed and shared, add a
permanent redirect in `next.config.ts`:

```ts
async redirects() {
  return [
    {
      source: '/blog/the-old-slug',
      destination: '/blog/the-new-slug',
      permanent: true,
    },
  ];
},
```

The title, meta tags, canonical URL, OG image, WhatsApp prefilled message, older/newer
links, "keep reading" cards, sitemap and RSS feed are all derived from the frontmatter and
the filename, so they update automatically. Only the URL needs the redirect.

## 8. Cross-references

The blog and the guides link into each other automatically:

- `/blog` shows a "Start with a guide" band
- `/guides` shows a "From the blog" band with your two most recent posts
- `/resources` links to both

To point a post at a guide, use a normal link in the body:

```mdx
See the [Docker guide](/guides/does-my-business-need-docker) for the business case.
```

Internal links are handled as `next/link` automatically by `mdx-components.tsx`.
